# 技术决策地图

## 1. 做得最好的三个技术决策

### 决策 1：接口抽象 + 可插拔 ＞ 硬编码实现

**工程判断**：RAG pipeline 的 `StorageAdapter`、`EmbeddingProvider`、`Reranker`、`QueryRewriter`、`QueryRouter`、`SemanticCache` 全部是接口定义。生产实现（PgVectorStorage、CohereReranker、LLMQueryRewriter）和开发/mock 实现（InMemoryStorage、NoopReranker、NoopQueryRewriter）自由互换。

**为什么好**：
- 切换向量数据库（pgvector → Pinecone）只需改写 `PgVectorStorage` 内部，接口不变
- 单元测试不需要 PostgreSQL — `InMemoryStorage` 就是纯 Map
- rag-core 包不依赖任何 LLM — `callDeepSeekJSON` 通过回调注入，保持 LLM 无关

**代码证据**：`packages/rag-core/src/storage.ts` 的 `StorageAdapter` 接口 + `InMemoryStorage` 实现 + `pgvector-storage.ts` 的生产实现。`rag-init.ts` 的 `initRagPipeline(callDeepSeekJSON?)` 回调注入模式。

---

### 决策 2：HITL 全流程人工审核，AI 绝不自动发送

**工程判断**：所有 AI 草稿进入 `awaiting_approval` 状态（Worker `index.ts:549`），所有 chat 消息生成和发送是两个独立步骤（`chat-window.tsx:127` vs `151`）。AI "辅助而非替代"不是 slogan，是架构级的 hard boundary。

**为什么好**：
- 一条错误的 AI 消息发出去后，品牌损害不可逆
- 全自动 = 接受 prompt injection 风险 × LLM 幻觉风险，双重放大
- HITL 审核的成本（人力延迟）远低于一次 AI 事故的代价

**代码证据**：
- `apps/worker/src/index.ts:546-548` — "AI draft is saved as a message but NEVER auto-sent"
- `apps/web/components/chat/chat-window.tsx` — `handleAiDraft` (生成) 和 `handleSendDraft` (发送) 是两个独立回调
- Message.reviewAction 字段 — 记录了 approved/rejected 的 HITL audit trail

---

### 决策 3：优雅降级链条，不做硬依赖

**工程判断**：每个外部依赖都有 fallback。Embedding API 不可用 → 关键词搜索。Redis 不可用 → 内存回退 + fail-open。Cohere API 未配置 → NoopReranker。JWT 黑名单 Redis 不可用 → fail-open（仍允许 token）。Sentry DSN 未设 → 只不追踪，不报错。

**为什么好**：
- 新人 clone 代码后不需要配 5 个 API key 就能跑起来
- 任何一个外部服务挂掉，系统不会完全不可用
- 每种降级都明确告诉了用户（或开发者）当前在用什么

**代码证据**：
- `keyword-search.ts` — tsvector FTS 失败 → `content ~* $1` regex fallback
- `rate-limit.ts` — Upstash REST 不可用 → 内存 Map + TTL
- `reranker.ts:93-95` — `createReranker()` 工厂函数自动 fallback

## 2. 最大的三个技术债

### 债务 1：测试覆盖空白（严重度：高，修复成本：中）

**现状**：54 个测试全是纯函数/逻辑测试。API 路由、Worker、RAG pipeline、WebSocket — 零测试覆盖。

**影响**：每次改 `messages/route.ts`、`ai-draft/route.ts`、`hybrid-retriever.ts` 时没有安全网。上周 inbox 重构改了 15 个文件——其中 3 个是 API 路由——没有任何自动化测试验证它们的正确性。

**修复路径**：
1. 给 `messages/route.ts` 的 POST handler 加单元测试（mock Prisma, 验证 reviewAction 写入）— 2 小时
2. 给 `ai-draft/route.ts` 的 `searchKnowledgeBase` 函数写隔离测试（mock hybridRetrieve）— 1 小时
3. 给 `hybrid-retriever.ts` 写纯函数测试（mock embedder + sql, 验证 RRF fusion 正确性）— 3 小时
4. Worker consumer 集成测试（需要 Redis Container）— 4 小时

---

### 债务 2：AICallMetric 缺字段 — kbChunksUsed, confidenceFailed（严重度：中，修复成本：低）

**现状**：`AICallMetric` 记录了 LLM 调用的 token 和延迟，但不记录 RAG pipeline 的核心指标——KB 命中数和 Confidence Gate 触发次数。

**影响**：AI 指标看板上 KB 命中率显示"数据待接入"，Confidence Gate 频繁触发但运维不知道。

**修复路径**：
1. Schema 加 `kbChunksUsed Int?` + `confidenceFailed Boolean?` — 1 行 Prisma diff
2. `ai-draft/route.ts:113-124` 的 `AICallMetric.create` 加字段 — 2 行
3. `hybridRetrieve` 返回 `secondaryRetrievalUsed` 已就绪 — 在调用方写入 AICallMetric
4. `metrics/ai/route.ts` 的 kbHitRate 从 `null` 变成真实聚合 — 5 行

**总成本**：4 个文件，~40 行代码。

---

### 债务 3：Chat / Email 双路径维护成本（严重度：中，修复成本：高）

**现状**：WebSocket (socket-server.ts) 和 REST (chat-messages/route.ts) 两条消息路径各自维护。修复安全漏洞（如 5000 字符上限）要改两处。WebSocket 的 JWT 验证不查黑名单。

**影响**：每次改动聊天功能都要确认两条路径一致。生产环境容易出现"REST 路径修了但 WS 路径没修"的安全漏洞。

**修复路径**：抽取共享的 message validation + persistence 逻辑到一个函数，WebSocket 和 REST 都调它。这个改动涉及 socket-server.ts 和 chat-messages/route.ts 两个文件的重构，约 2 小时。

## 3. 100 组织 × 10 万消息/天的瓶颈分析

### 爆点预测

| 组件 | 当前上限 | 100 orgs / 10万 msgs/day | 瓶颈 |
|------|---------|--------------------------|------|
| **PostgreSQL** | 免费 tier (pgBouncer, ~15 并发) | 10万 msg × 每条 avg 3 次 DB 查询 = 30 万次查询/天 ≈ 3.5 QPS 平均。高峰期 10x = 35 QPS | **连接池先爆** — `connection_limit=1` 的 Serverless 实例数 > pgBouncer 最大连接数 |
| **DeepSeek API** | 免费 tier (速率限制未知) | 10万 msg 约 30% 触发 AI 草稿 = 3 万次 API 调用/天 ≈ 0.35 QPS 平均 | **不会爆** — DeepSeek 有独立的 rate limit，但 0.35 QPS 远低于限制 |
| **Redis (Upstash)** | 免费 500K 命令/天 | 10万 msg × 每条 2 次限流检查 + 队列操作 ≈ 30 万/天 | **接近上限** — 再加缓存读写可能超 |
| **Vercel** | Hobby tier (100GB 带宽, 有限执行时间) | 100 orgs × 每 org 平均 5 活跃用户 × 每天 50 次页面加载 = 2.5 万次 SSR/天 | **Bandwidth 先爆** — SSR 渲染返回 HTML 比 SPA 大 |
| **BullMQ (Railway)** | 单 Worker 进程, concurrency 5+5+3+3=16 | 10 万 msg 处理: compose-reply ≈ 3 万 job/天 ≈ 0.35 QPS | **不会爆** — 16 并发远超 0.35 QPS |

### 改造路径

1. **PostgreSQL**：升级 Supabase 到付费 tier + 调大 pgBouncer pool。或者引入 Read Replica 分流分析查询
2. **Redis**：Upstash 付费 tier 或自建 Redis。semantic cache 的 key 数量随 org 数线性增长，加 TTL 做不到完全管控——需要 key 数量监控
3. **Vercel**：升级 Pro tier ($20/月)。或者把不敏感的页面（analytics, home）加 ISR revalidate=60s 减少 SSR 压力
4. **Worker**：单实例 concurrency 16 → 需要时加实例（BullMQ 天然支持多 Worker）。Railway 水平扩展付费用

## 4. 和 Intercom / Zendesk AI 的技术差异化

| 维度 | SalesAgent AI | Intercom Fin | Zendesk AI |
|------|-------------|-------------|-----------|
| **RAG 技术** | 自研 6 阶段 pipeline（Query Rewriter → Router → Hybrid Search → RRF → Reranker → Confidence Gate） | GPT-4 + 知识库，但 pipeline 细节不透明 | 类似的 RAG，但不开源 pipeline 细节 |
| **LLM** | DeepSeek（中国部署友好，成本低） | GPT-4（英语强，价格高） | 自研 + GPT 混合 |
| **HITL** | 所有 AI 草稿强制人工审核 | 支持 Agent handoff 但无系统级 HITL | 类似 |
| **嵌入模型** | 可插拔（OpenAI/DeepSeek/SiliconFlow Qwen3-4B），支持 Matryoshka 维度 | OpenAI only | 未公开 |
| **Reranker** | Cohere Rerank + Noop fallback | 内置 | 内置 |
| **语义缓存** | Redis 两层 (exact + cosine≥0.95) | 未公开 | 未公开 |
| **多租户** | 从底层 DB 列做 org-scoped 隔离 | SaaS 内置 | SaaS 内置 |
| **私有化部署** | 企业版支持 | 不支持 | 不支持（仅 Zendesk Suite） |
| **中文支持** | 一流（DeepSeek 中文原生 + bigram 分词） | 有限 | 有限 |
| **定价** | ¥1,999-19,999/月 | $99-999/月 | $55-215/agent/月 |

### 技术差异化总结

1. **RAG pipeline 全自研** vs 竞品的黑盒 LLM 调用 — 这意味着检索质量的每个环节都可调试、可优化、可替换
2. **私有化部署 + 中国合规** — 竞品在私有化上通常是短板
3. **全链路可见性** — AICallMetric 记录了每次调用的 token/延迟/成功/降级/错误类型 — 竞品通常不暴露这些指标
4. **劣势** — 缺乏第三方集成生态（Intercom 有 300+ app marketplace），缺乏全球 CDN 和低延迟 infra（中文市场不需要但海外需要）

## 5. 面试深挖与坦白指南

### 最值得深挖的（准备详细解释）

| 点 | 为什么值得挖 | 准备什么 |
|----|------------|---------|
| **RAG pipeline 设计** | 这是项目最硬核的技术点。6 阶段自研 pipeline 在面试中会引发体系化追问 | RRF 公式、Confidence Gate 阈值为什么是 0.7、How to improve Precision@5 |
| **HITL 状态机** | 体现了产品 sense 和工程判断 — "AI 绝不自动发送"是你可以展开讲的核心价值观 | 审核疲劳、半自动化的 tradeoff、如果重来一次会怎么设计 |
| **安全纵深防御** | 9 层安全链 + prompt injection 防护，面试官会问你有没有实际测试过攻击向量 | PROMPT_ARMOR 的局限、safe() 误用历史的坦诚检讨、更好的方案 |
| **Monorepo 架构决策** | package 间依赖关系、为什么 ai-core 不引 rag-core、为什么 worker 单独部署 | Turborepo pipeline、循环依赖预防、Vercel + Railway 双部署的原因 |

### 需要提前准备"坦白"的

| 点 | 怎么坦白 |
|----|---------|
| **测试覆盖只到纯函数层** | "54 个测试覆盖了权限矩阵、JWT 验证、bcrypt 哈希、prompt builder、限流回退 — 这些都是改了会炸的关键路径。API 和 Worker 的集成测试是已知债务，优先级在团队超过 2 人之前排" |
| **Confidence Gate 阈值是拍的** | "0.7 是一个合理的初始值——但我知道它没有校准。如果要生产化，我会在 eval 集上画 top-1 score 分布直方图，找出区分 '有相关结果' 和 '无相关结果' 的最佳 ROC 分界点" |
| **前端 state 管理可以更好** | "inbox 的 7 个 useState 有链式 re-render 风险，但一个人开发时这个不是瓶颈。团队变大会抽 useInboxMessages hook 或用 useReducer 统一管理" |
| **Semantic Cache 的 0.95 阈值没有实验依据** | "FAQ 场景下 cosine 相似度分布在 0.90-0.98 的区间，0.95 偏高——可能漏掉一些语义相似的查询。降低到 0.85 的风险是误匹配。应该在生产环境记录 cosine 分布后再调" |
| **Worker 的 retryCount 恒为 0** | "BullMQ 的重试发生在队列层——Worker 代码里看不到 retry 计数。AICallMetric 的 retryCount 字段写到 DB 时恒为 0 因为每次重试都是新的函数调用。这是一个设计疏忽——应该在 job.attemptsMade 写入时同步给 AICallMetric" |

## 最终总结

SalesAgent AI 是一个有清晰架构理念的全栈项目。技术上的核心资产是：

1. **RAG pipeline** — 6 阶段自研检索管线，接口抽象，可插拔
2. **HITL 全流程** — "AI 辅助而非替代"贯穿架构设计
3. **优雅降级** — 每个外部依赖都有回退方案
4. **全链路可观测性** — AICallMetric + metrics API + 四层看板

技术债分布上：测试覆盖（高/中）、AICallMetric 字段（中/低）、双路径维护（中/中）。前两项可在一周内消化，第三项需要重构。

如果要面试，把 RAG pipeline 的 6 个阶段吃透（尤其是 RRF fusion 和 Confidence Gate 的设计理由），把 HITL 的 tradeoff 想清楚（半自动化的风险收益分析），把安全机制的层层叠加讲清楚（9 层防御的逻辑关系）。这三个点讲好了，其他东西都是佐证。
