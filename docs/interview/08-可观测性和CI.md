# 模块 8：可观测性和 CI

## 结论

可观测性由三层组成：AICallMetric（数据库级）、AI Health Dashboard（前端级）、AI 四层指标看板（业务级）。CI 有三个并行 job，互不依赖。54 个测试全部是纯函数/逻辑测试，API 路由和 Worker 逻辑没有测试覆盖。RAG eval 的 Precision@5=0.62 是用 mock retriever + 实际 KB 文件测出来的。draftAdoptionRate 等 reviewAction 数据积累一周后接上即可。

## 2. 54 个测试的覆盖边界

### 有覆盖的

| 域 | 文件 | 覆盖内容 |
|----|------|---------|
| 权限 | permissions.test.ts (14) | hasPermission() 对所有角色×权限的组合正确性, requirePermission 抛异常 |
| 认证 | auth.test.ts (8) | JWT sign/verify round-trip, 拒绝空/garbage/tampered/不同密钥的 token |
| 密码 | password.test.ts (7) | bcrypt hash/verify, 相同密码不同盐, 错误/空/相似密码 |
| AI 提示 | ai.test.ts (18) | 4 个系统提示包含必需字段, 3 个 prompt builder 正确渲染, 4 个 feature flag 默认值 |
| 限流 | rate-limit.test.ts (5) | 内存限流: 允许前 100, 拒绝 101+, 不同 IP, fail-open |
| 集成 | injection.test.ts (excluded) | 被排除——需要真实 DeepSeek API 做 prompt injection 攻击测试 |
| API | api-*.test.ts (8 files, excluded) | 全部被排除——需要 DATABASE_URL |

### 完全没有覆盖的

| 路径 | 风险等级 | 为什么危险 |
|------|---------|-----------|
| `messages/route.ts` POST | **高** | 消息写入逻辑（reviewAction, cursor 分页, channel 过滤）— 零测试 |
| `ai-draft/route.ts` | **高** | RAG pipeline + LLM 调用—50 行核心逻辑零测试 |
| `hybrid-retriever.ts` | **高** | RRF fusion, confidence gate, reranker—零单元测试 |
| `semantic-cache.ts` | **中** | 两层缓存逻辑—零测试, 依赖 Redis mock |
| `socket-server.ts` | **中** | WebSocket 认证 + 消息持久化—零测试 |
| `score-lead/route.ts` | **中** | Worker 入队逻辑—零测试 |
| Worker 4 个 consumer | **中** | AI compose, email send, campaign step, scoring—零测试 |
| RBAC 路由级检查 | **中** | 每个 route handler 的 checkPermission 只是代码规约, 无测试验证 |

### 最高的未覆盖风险

**`messages/route.ts` 的 POST handler**——这是用户发送消息的唯一入口。如果 Zod schema 变更（如 reviewAction 加了但你忘了改 Prisma create），生产环境会静默失败（Zod 的 safeParse 不会抛异常，只是返回 400，但如果 reviewAction 是 optional 就不会有 400，而是 reviewAction 字段根本没写入 DB）。

## 3. CI 的三个 job

### 关系

```
CI workflow (3 jobs, 并行, 无依赖)
┌─────────────────┐  ┌──────────────────────┐  ┌─────────────────┐
│ unit-test        │  │ type-check-packages   │  │ rag-eval        │
│ ─ 54 unit tests  │  │ ─ ai-core tsc         │  │ ─ retrieval eval│
│ ─ web tsc        │  │ ─ rag-core tsc        │  │ (optional)      │
│                  │  │ ─ worker tsc          │  │                 │
└─────────────────┘  └──────────────────────┘  └─────────────────┘
```

它们之间没有 `needs:` 依赖。`type-check-packages` 失败了，`unit-test` 还是会跑完——反之亦然。

### 共通前置

每个 job 都要跑 `pnpm install --frozen-lockfile` + `prisma generate`——这是 monorepo 的代价（每个 job 独立 runner，不能共享 node_modules）。总 CI 耗时 ≈ 最慢的那个 job（通常 unit-test 因为有 54 个测试，包括 bcrypt 12 轮的耗时）。

### 为什么 rag-eval 是 optional

`if: ${{ env.EMBEDDING_API_KEY != '' }}` 在 step 级别检查。如果 GitHub Secrets 没配 `EMBEDDING_API_KEY`，整个 step 跳过。rag-eval job 只有这一个 step——所以 job 本身虽然触发，但实际不跑任何东西。

## 4. RAG eval 的 Precision@5=0.62

### 测量条件

- **数据集**：30 条 SalesAgent 领域 Q&A（启云科技产品/定价/FAQ/竞品/案例）
- **检索器**：mock retriever——从 KB 文件（4-6 份 .md）按段落分块，用关键词匹配 + 简单 TF-IDF 评分
- **指标**：50 次检索，取 top-5 结果，计算命中 ground truth chunk 的比例
- **LLM Judge**：未使用（`--retrieval-only`）
- **评测环境**：本地 CLI，非真实 pgvector

### 换一批问题会不会差很多

30 条是相对小的样本。Precision@5 的 95% 置信区间约 ±0.10-0.15（取决于方差）。换一批问题浮动 5-10% 是正常的。

更重要的是：mock retriever 的检索质量和真实 pgvector + Cohere Reranker 的检索质量**不是一个量级**。真实环境的 Precision@5 可能在 0.5-0.7 范围内，取决于：
- 是否配了 EMBEDDING_API_KEY（有=向量搜索，无=关键词 only）
- 是否配了 COHERE_API_KEY（有=Reranker 精排，无=RRF 原始排序）
- KB 文档的质量（启云科技的 4 份文档 vs 真实客户的 50+ 份文档）

## 5. 最小可行的 E2E 测试方案

### 需要解决的问题

1. **PostgreSQL + pgvector** — 需要一个带 pgvector 扩展的 PostgreSQL。本地用 Docker (`pgvector/pgvector:pg16`)，CI 用 GitHub Service Container
2. **Redis** — BullMQ + 限流需要。本地用 Docker (`redis:7-alpine`)，CI 用 Service Container
3. **环境变量** — JWT_SECRET, DATABASE_URL, DIRECT_URL, REDIS_URL
4. **Prisma migrate** — 需要先在测试 DB 上跑 push/setup-vector.mjs
5. **Seed 数据** — 一个最小 org（1 user, 1 agent, 1 lead, 1 conversation, 2 messages）

### 最小方案

```yaml
# 只测一条端到端路径作为 smoke test:
1. POST /api/auth/login → 拿到 JWT cookie
2. GET /api/orgs/{slug}/conversations → 200 + JSON
3. POST /api/orgs/{slug}/conversations/{id}/messages → 201 + message
4. 验证: 写入的 message 在 conversation.messages 中可见
```

### 为什么不现在就做

- 需要 GitHub Actions 配 Service Container（PostgreSQL + pgvector + Redis），network 配置容易踩坑
- E2E 测试跑一遍 >5s（含 Prisma push + seed），CI 总耗时增加
- 当前一个人开发，每次 push 用手动验证（localhost + curl）已经够用

建议：团队超过 2 个人之前不做 E2E CI。

## 6. draftAdoptionRate 接上的步骤

### 等数据积累一周后

`metrics/ai/route.ts` 里的 `draftAdoptionRate` 当前返回值是 `null`。前端看到 `null` 显示 "数据待接入"。

**改法**（一行都不需要改前端）：
```typescript
// metrics/ai/route.ts — 替换 const draftAdoptionRate = null;
const reviewStats = await prisma.message.aggregate({
  where: {
    conversation: { organizationId: orgId },
    reviewAction: { not: null },
    createdAt: { gte: from },
  },
  _count: { reviewAction: true },
});
const approvedCount = await prisma.message.count({
  where: {
    conversation: { organizationId: orgId },
    reviewAction: "approved",
    createdAt: { gte: from },
  },
});
const draftAdoptionRate = reviewStats._count.reviewAction > 0
  ? Math.round((approvedCount / reviewStats._count.reviewAction) * 100) / 100
  : null; // 仍然 null 如果时间段内零条 reviewAction 记录
```

**`null` 的逻辑**：如果时间段内零条 reviewAction 记录 → 仍然返回 `null` → 前端显示 "数据待接入"。这比返回 0% 正确——0% 会被解读为 "所有草稿被拒绝"，而实际只是还没开始记录。
