# 模块 6：安全机制

## 结论

安全体系是 9 层纵深防御：IP 验证 → 限流 → Session cookie → JWT → 黑名单 → Membership → RBAC → Zod 校验 → Org-scoped 查询。JWT 自实现用 jose 库（Edge 兼容），HS256 签名 + 7 天过期 + Redis 黑名单做登出。RBAC 是 5 角色 × 13 权限矩阵。WebSocket 认证走独立 JWT cookie 验证。safe() 函数只去换行——在当前代码中已从聊天消息路径摘除。Prompt injection 防护靠 `<user_data>` 标签 + PROMPT_ARMOR 系统提示。

## 1. JWT 自实现的完整细节

### 签名算法

```typescript
// lib/auth.ts:27-33
return new SignJWT({ ...payload, jti: generateId() })
  .setProtectedHeader({ alg: "HS256" })      // 对称加密
  .setIssuedAt()                               // iat claim
  .setExpirationTime("7d")                     // exp claim = issuedAt + 7 days
  .sign(JWT_SECRET);                           // Uint8Array from env var
```

- **HS256 (HMAC-SHA256)**：对称加密——签名和验证用同一个密钥。没有用 RS256（非对称），因为没有多服务之间的 JWT 传递需求。
- **JTI (JWT ID)**：每次签发包含一个 UUID v4 随机 ID。用于登出时加入黑名单。

### Payload 结构

```typescript
export interface JwtPayload {
  userId: string;     // Prisma User UUID
  email: string;      // 用户邮箱
  name: string | null; // 用户显示名
  orgId: string;      // 当前组织 UUID
  orgSlug: string;    // 当前组织 slug (URL 使用)
  role: string;       // owner | admin | operator | viewer | customer
  jti: string;        // JWT ID (用于黑名单)
}
```

### 过期时间

- **7 天 (604800 秒)**：行业标准平衡——足够方便不被频繁打断，足够安全不会永久有效
- 没有 refresh token——JWT 过期后用户重新登录

### 黑名单的 Redis key 结构

```typescript
// lib/token-blacklist.ts
const key = `session:revoked:${jti}`;
// 值: "1"
// TTL: 7 天 (与 JWT 同生命周期)
// 操作: SET with EX — Redis 自动过期，不需要手动清理
```

### 为什么不用 NextAuth/Auth0

1. **JWT 的 payload 需要自定义字段**（orgSlug, role）——OAuth token 不含这些
2. **Edge Runtime 兼容**——NextAuth 在 middleware 中有限制
3. **零外部依赖**——不需要维护 OAuth provider 的回调 URL、token 刷新逻辑
4. **B2B 场景**——Email + password 是企业内部工具的标准登录方式

## 2. RBAC 的 5 角色 × 13 权限矩阵

### 完整矩阵

| 权限 | owner | admin | operator | viewer | customer |
|------|-------|-------|----------|--------|----------|
| manage_org | ✅ | - | - | - | - |
| manage_members | ✅ | ✅ | - | - | - |
| manage_agents | ✅ | ✅ | ✅ | - | - |
| manage_leads | ✅ | ✅ | ✅ | - | - |
| delete_leads | ✅ | ✅ | - | - | - |
| manage_campaigns | ✅ | ✅ | ✅ | - | - |
| view_agents | ✅ | ✅ | ✅ | ✅ | - |
| view_leads | ✅ | ✅ | ✅ | ✅ | - |
| view_members | ✅ | ✅ | ✅ | ✅ | - |
| view_audit_log | ✅ | ✅ | ✅ | ✅ | - |
| run_campaigns | ✅ | ✅ | ✅ | - | - |
| manage_api_keys | ✅ | ✅ | - | - | - |
| view_api_keys | ✅ | ✅ | - | - | - |

### customer 角色为什么是零权限

`customer` 角色不在 PERMISSION_MAP 的任何权限列表中（`hasPermission("customer", any)` 永远返回 false）。客户的授权不是通过 RBAC 权限，而是通过 **数据行级别的 scoping**：

```typescript
// chat-messages/route.ts — customer 权限检查
if (session.role === "customer") {
  const lead = await prisma.lead.findFirst({
    where: { id: conversation.leadId, userId: session.userId },
  });
  if (!lead) return NextResponse.json({ error: "Access denied" }, { status: 403 });
}
```

customer 只能看到 `Lead.userId === customer.id` 的对话。这不是 RBAC，是 **resource-level ACL**。

### operator 和 viewer 的边界

| 差异 | operator | viewer |
|------|----------|--------|
| 创建/编辑 Agent | ✅ manage_agents | ❌ |
| 创建/编辑 Lead | ✅ manage_leads | ❌ |
| 删除 Lead | ❌ delete_leads | ❌ |
| 创建/编辑 Campaign | ✅ manage_campaigns | ❌ |
| 运行 Campaign | ✅ run_campaigns | ❌ |
| 查看所有数据 | ✅ | ✅ |
| 查看 API Keys | ❌ | ❌ |

viewer 是只读角色——能看到所有数据但不能做任何修改。operator 能做日常操作（管理 lead、agent、campaign），但不能删 lead 或管理 API keys。

## 3. WebSocket 认证

### socket-server.ts 的 auth middleware

```typescript
// socket-server.ts:45-66
io.use(async (socket, next) => {
  // Parse JWT from cookie (same format as Next.js middleware)
  const cookieHeader = socket.handshake.headers.cookie || "";
  const cookies = Object.fromEntries(
    cookieHeader.split("; ").filter(Boolean).map((c) => {
      const [key, ...rest] = c.split("=");
      return [key, rest.join("=")];
    })
  );
  const token = cookies["session"];
  if (!token) return next(new Error("Authentication required"));

  const payload = await verifyToken(token);
  if (!payload) return next(new Error("Invalid or expired token"));

  (socket as any).user = payload;
  next();
});
```

### 和 HTTP JWT 验证的区别

| 维度 | HTTP middleware | WebSocket auth |
|------|----------------|----------------|
| Token 来源 | httpOnly cookie (自动带) | 手动解析 cookie header |
| 黑名单检查 | ✅ isTokenRevoked() | ❌ 不做——已登出的 token 仍可用于 WS 连接 |
| 限流 | ✅ 100/min | ❌ 没有限流（5000 字符上限替代） |
| Edge 兼容 | ✅ | N/A（独立 Node.js 进程） |
| 失败响应 | 401 JSON / 302 redirect | `next(new Error("..."))` + socket disconnect |

### 关键缺口

**WebSocket 不检查 JWT 黑名单**——如果用户在 HTTP 端登出（JTI 加入 Redis 黑名单），已建立的 WebSocket 连接不会被断开。`verifyToken` 只检查签名和过期时间，不查 `isTokenRevoked()`。这是一个安全缺口。

## 4. safe() 函数

### 实际实现

```typescript
// packages/ai-core/src/prompts.ts:53-55
export function safe(s: string): string {
  return s.replace(/[\r\n]/g, " ").trim();
}
```

### 作用

只去掉换行符（`\r`, `\n`）并 trim——**防止 prompt injection smuggling**：攻击者通过 `\n\nIgnore all previous instructions...` 从 `<user_data>` 标签内逃逸出来。

### 误用历史

在 Phase 21 之前，`chat-messages/route.ts` 用了 `safe(content)` 清洗聊天消息：
```typescript
// 旧代码 — 已修复
content: safe(content),  // ← 错误：聊天消息不进 LLM prompt，不需要防注入
```

**为什么误用**：`safe()` 的命名暗示它是通用安全清洗函数，但实际上它只去掉换行符。如果消息包含换行（多行聊天消息），`safe()` 会把换行吃掉，破坏用户输入。

**修复**（Phase 22）：从 chat-messages route 移除 `safe()`，只在 ai-draft 的 prompt 构建时用 `safe()` + `<user_data>` 标签双重防护。

## 5. Prompt injection 防护的深入分析

### 当前方案的三层防护

```
Layer 1: PROMPT_ARMOR — 系统提示指示 LLM 忽略 <user_data> 内的指令
Layer 2: <user_data> 标签 — 明确标记哪些是用户输入
Layer 3: safe() — 去除换行符，防止标签逃逸
```

### 局限性

1. **依赖 LLM 遵守指令**——如果 LLM 被 jailbreak，`<user_data>` 标签形同虚设
2. **没有输出验证**——即使 PROMPT_ARMOR 要求 "Output only the requested JSON format"，代码没有在 LLM 响应后验证是否真的只有 JSON
3. **safe() 太弱**——只去换行，不去特殊 XML 字符。`<user_data>` 本身是用 XML 标签实现的，`safe()` 不防 `</user_data>` 注入

### 更完善的方案

1. **输入序列化**：把用户输入编码为 base64，从根本上消除注入可能性
2. **输出验证**：在 `callDeepSeekJSON` 的 `extractBalancedJSON` 基础上，加 schema 验证（Zod）确保响应确实符合预期格式
3. **双模型架构**：用一个小模型（如 DeepSeek-chat-lite）做安全裁判，在发送前检查 AI 生成的内容是否有异常

## 6. customer 角色的跨组织数据拦截

### 如果有人通过 customer 角色尝试访问其他 org 的数据

**拦截层级**：

```
Layer 1 — Conversation 存在性检查
  chat-messages/route.ts:29
  prisma.conversation.findUnique({ where: { id: params.id } })
  → 不存在? 404 "Not found"

Layer 2 — Membership 检查 (agent/operator 路径)
  chat-messages/route.ts:34
  if (membership && conversation.organizationId !== membership.organizationId)
  → 不匹配? 404 "Not found" (不区分"不存在"和"没权限")

Layer 3 — Customer scoping (customer 路径)
  chat-messages/route.ts:38-42
  prisma.lead.findFirst({ where: { id: conversation.leadId, userId: session.userId } })
  → lead 不属于该 customer? 403 "Access denied"

Layer 4 — URL 参数伪造
  customer 尝试访问 /api/orgs/other-org-slug/conversations/...
  → middleware: verifyToken → JWT payload.orgSlug 不等于 URL slug?
  → 不验证。middleware 只检查 JWT 是否有效，不检查 orgSlug 匹配
  → 进到 Route Handler 后: membership 查询 { userId, organization: { slug } }
  → customer 没有 membership → 返回 404
```

**关键**：customer 没有 membership 行。所有靠 `membership.findFirst` 守门的路由，对 customer 返回 404。customer 只能走特殊路径（如 chat-messages）——这些路径里有 `Lead.userId` 检查。
