# 模块 7：防幻觉机制

## 结论

系统有 5 层防幻觉机制，从检索到输出逐层收缩。Confidence Gate 和 HITL 审核是两级不同的防线——一个防召回失败，一个防生成错误。系统设计遵循"宁愿不回答也不编造"的原则，但知识库内容过期或冲突时没有自动检测，也没有对持续幻觉的自动化监控。

---

## 1. 五层防幻觉机制

### 层级图

```
用户 query
    │
    ▼
[Layer 1: RAG Pipeline — 基于知识库回答]
  检索相关 chunks → 注入 LLM prompt
  作用: LLM 只能基于检索到的事实回答
  局限: 检索本身可能失败（0 相关结果 or 检索到不相关内容）
    │
    ▼
[Layer 2: Confidence Gate — 低分检索二次搜索]
  top-1 score < 0.7 → 放宽 topK → 用原始 query 再搜一次
  作用: 捕获第一次搜索漏掉的相关结果
  局限: 阈值 0.7 是拍脑袋的，没有校准
    │
    ▼
[Layer 3: PROMPT_ARMOR + 系统提示 — 行为约束]
  "知识库没有的信息，诚实说'我确认一下再回复'，绝不编造"
  "产品功能、定价、竞品对比等信息必须从知识库引用"
  作用: 指示 LLM 在没有事实依据时不编造
  局限: 是 soft defense，依赖 LLM 遵守指令的能力
    │
    ▼
[Layer 4: <user_data> 标签 + safe() — 输入清洗]
  所有用户输入包裹在 <user_data> 标签内
  PROMPT_ARMOR 指示 LLM 忽略标签内的指令
  safe() 去换行防止标签逃逸
  作用: 防止 prompt injection 导致 LLM 行为异常
  局限: safe() 只去换行，不防 XML 标签注入
    │
    ▼
[Layer 5: HITL 审核 — 人工把关]
  AI 草稿标记为 awaiting_approval
  人工审核后才能发送
  作用: 阻断 AI 生成的危险内容到达客户
  局限: 审核疲劳、批量审核时跳读
```

### 各层之间的互补关系

| 场景 | Layer 1-2 | Layer 3 | Layer 4 | Layer 5 |
|------|-----------|---------|---------|---------|
| 知识库里没有相关内容 | KB context 为空 → LLM 应该拒绝回答 | 提醒 LLM 诚实 | N/A | 如果 LLM 还是编了，审核可拦截 |
| 知识库有内容但检索失败 | Confidence Gate 二次搜索 | N/A | N/A | 草稿质量差 → 审核拒绝 |
| Prompt injection 攻击 | N/A | LLM 可能被劫持 | safe() + 标签防护 | 审核拦截异常回复 |
| LLM 幻觉（编造产品功能） | KB context 正确但 LLM 无视 | 提示约束 | N/A | 审核拦截 |

---

## 2. Confidence Gate vs 防幻觉

### 两者区别

**Confidence Gate 是防"召回失败"**——检索引擎没有找到相关 chunk。这个和 LLM 幻觉无关。检索失败了，LLM 收到的 context 是空的或无关的——此时 LLM 按指令应该回复"我不知道"，但 LLM 可能还是会编造（幻觉）。Confidence Gate 不防这一点。

**防幻觉是 Layer 3-5 的职责**——让 LLM 在 context 不够时不编造。而这完全是 soft defense。

### 实际场景

```
用户: "你们的 OAuth SSO 怎么配？"
KB: 有"SSO 配置指南"但讲的是 SAML，没有 OAuth

Confidence Gate: top-1 score = 0.75（SAML 文档和 "OAuth" 词无直接匹配但语义接近）
→ 不触发二次搜索

LLM 收到的 context: SAML SSO 文档（不包含 OAuth 信息）
PROMPT_ARMOR 约束: "知识库没有的诚实说不知道"

LLM 可能的行为:
A) 正确: "知识库里主要讲 SAML SSO，OAuth 的具体配置我需要确认后再回复"
B) 幻觉: 从 SAML 配置推断出 OAuth 配置（编造）
C) 混合: "你可以用 SAML（引用 KB）...OAuth 的话我们也支持（编造）"
```

Confidence Gate 不会防 B 或 C——它能做的都做了（查到了相关 chunk，分数也不低）。这个问题本质上是 LLM 在没有事实依据时的行为不可控。

## 3. HITL 审核的局限性

### 审核疲劳

`awaiting_approval` 状态的对话在 Inbox 显示橙色 ⏳ 待审核徽章。如果审核员每天要审 50 条草稿：
- 第 1-10 条：认真看
- 第 11-30 条：快速扫一眼
- 第 31-50 条：直接点 "发送"（信任 AI）

### 批量审核的风险

系统没有防批量审核的机制：
- 没有 "连续批准" 的限流
- 没有 "相似草稿全部批准" 的提示
- 没有 "草稿中包含新事实（不在 KB 中）" 的告警

### 改进方向

1. **风险评分**：给每条草稿打风险分（检索质量 + 是否引用了 KB + 是否包含不常见的声明）
2. **抽样审核**：低风险草稿自动发送，高风险草稿强制人工审核。审核疲劳反而因为量少而缓解
3. **审核统计**：记录每个审核员的批准/拒绝比例，检测"只批不绝"的审核员

## 4. "打错比打不出来更危险"的代码体现

### 具体体现

1. **PROMPT_ARMOR 指令**（`prompts.ts:5-9`）："知识库没有的信息，诚实说不知道，绝不编造"
2. **ai-draft 系统提示**（`ai-draft/route.ts:76-82`）："知识库优先、基于事实回答、知识库没有的诚实说'我确认一下再回复'"
3. **HITL 状态机**（`index.ts:546-548`）："AI draft is saved as a message but NEVER auto-sent"
4. **Confidence Gate 触发**：检索质量低 → 自动 expanded search，不给 LLM 用低质量 context 编造的机会
5. **Chat 模式下没有 auto-send**：`chat-window.tsx` 的 `handleAiDraft` + `handleSendDraft` 需要两步操作（生成 + 发送），没有任何自动发送的路径

### 这个原则的代价

- 人工审核增加延迟（草稿生成到发送之间有几小时甚至几天）
- 审核负担随对话量线性增长
- 低风险场景（"你们的工作时间是几点"）也被迫走审核——浪费审核精力

## 5. 知识库过期和冲突处理

### 当前状态：无

系统没有：
- **文档版本管理**：上传同名文档会覆盖（通过 `content-hash.ts` 的 SHA-256 指纹判断是否更新），但旧版文档的历史痕迹丢失
- **冲突检测**：两份文档声称不同价格（"基础版 ¥1,999" vs "基础版 ¥1,599"），系统不知道它们冲突
- **时效性检查**：5 年前的定价文档和今年的定价文档在检索结果里平权

### 如果发生冲突

LLM 会收到两条矛盾的 chunk。当前 PROMPT_ARMOR 不会帮它解决冲突——LLM 可能：
- 随机选一条（如果矛盾没被注意到）
- 两条都提（"一个说 A，一个说 B"——让用户困惑）
- 写个模糊的回复（"价格视情况而定"—没用）

### 改进方向

1. 在 Document metadata 里加 `validFrom` 和 `validTo` 时间戳
2. 检索时加权：越新、越官方（如 "Pricing" 类型 > "Email" 类型）的文档分数越高
3. 冲突检测（可选）：定期用 LLM 扫描 KB，检测相矛盾的事实对，标记给管理员审核

---

## 6. 持续幻觉的检测和告警

### 当前状态：无

系统没有：
- **自动检测 LLM 输出是否包含在 KB 中**（faithfulness check）
- **幻觉频率监控**：连续多少条草稿被审核拒绝
- **异常告警**：草稿审核拒绝率突然飙升 → 可能是 prompt 被注入或 LLM 模型换版导致行为变化

### 为什么没做

- faithfulness evaluation（LLM-as-Judge）已在 eval 框架中实现（`eval/metrics.ts`），但只在 CLI 跑，没接入生产
- 生产环境每次草稿都跑 faithfulness check 会额外增加 LLM 调用（成本翻倍）
- AICallMetric 表记录了每次调用的成功/失败，但没有记录"被审核拒绝"

### 最小可行的监控方案

1. 在 `reviewAction = "rejected"` 时写入 AICallMetric（或单独表）
2. 如果 24 小时内拒绝率 > 30%，发告警
3. 保留被拒绝的草稿和 KB context 用于事后分析——找出幻觉的模式
