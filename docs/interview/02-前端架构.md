# 模块 2：前端架构

## 结论

Inbox 的前端架构核心是两个页面模式（list view / detail view）共享同一套 Client Component 状态机，通过 `selectedId` prop 控制。Server Component 负责首屏数据加载，Client Component 负责所有交互。消息通道（Email/Chat）通过 `channel` 字段在客户端过滤实现隔离，无需后端分表。

---

## 1. inbox-client.tsx 的核心状态机

### 7 个 useState + 3 个 useRef + 3 个 useMemo

```typescript
// ── 导航状态（最高频变化）
filter:     "all" | "active" | "needs_review" | "needs_reply" | "closed"
selectedId: string | null
chatMode:   boolean  // email ↔ chat toggle

// ── 数据状态
messages:   Message[]
replyDraft: string
aiDraft:    { subject, body, tone, suggestedAction } | null

// ── 加载状态（互斥的 UI 状态）
msgsLoading: boolean   // 初始消息加载
aiTyping:    boolean   // AI 正在生成
sending:     boolean   // 正在发送
generating:  boolean   // AI 草稿按钮 loading

// ── 分页状态（Phase 21 新增）
nextCursor: string | null
hasMore:    boolean
loadingMore: boolean
```

### 状态依赖图

```
filter 变化         → filtered 重新计算 (useMemo)
selectedId 变化     → messages 重新 fetch (useEffect)
                    → replyDraft / aiDraft 清空
chatMode 变化       → channelMessages 重新过滤 (useMemo)
messages 变化       → messagesEndRef scrollIntoView (useEffect)
replyDraft 变化     → 发送按钮 disabled 状态
aiDraft 变化        → 草稿气泡显示/隐藏
```

### 链式 re-render 风险

```
用户点击对话 → setSelectedId(id)
  → useEffect: fetch messages (async)
    → setMessages(data) → re-render 消息列表
    → setNextCursor, setHasMore → re-render 加载更多按钮
  → useEffect: scrollIntoView
  → setReplyDraft(""), setAiDraft(null) → re-render compose 区

总 re-render 次数: 3-4 次（React 18 自动批处理 state，但 async callback 内的 setState 不会被批）
```

**优化空间**：`selectedId` 变化时，消息列表、compose 区、详情 header 三者同时 re-render。可以用 `useMemo` 把 header 独立出来，避免不必要的 re-render。

## 2. Server Component vs Client Component 分工

### 为什么有些数据在服务端加载

```typescript
// page.tsx (Server Component) — 首屏数据
const conversations = await prisma.conversation.findMany({
  where: { organizationId: session.orgId },
  include: { lead, agent, messages(take:1) },
  take: 50,
});
// → 传给 InboxClient 作为 prop
// → props.conversations 直接渲染，不需要客户端 fetch
```

**原因**：
1. SSR 首屏渲染不需要 JS 就能看到对话列表
2. 服务端可以直接读 JWT cookie（`getSession()`），无需客户端再认证
3. Prisma 在服务端运行，不暴露 DB URL

### 为什么消息在客户端 fetch

```typescript
// inbox-client.tsx — useEffect
fetch(`/api/orgs/${orgSlug}/conversations/${selectedId}/messages?limit=50`)
```

**原因**：
1. 消息量大（可能有 50+ 条），不在首屏静态渲染中加载
2. 消息需要实时更新（发送后 append），在客户端管理更自然
3. 只加载已选中对话的消息——未选中的对话不需要拉消息
4. 支持 cursor 分页（`?cursor=&limit=50`），需要客户端维护 cursor state

## 3. Email/Chat 通道隔离

### channel 字段的过滤逻辑

```typescript
// inbox-client.tsx:161-169
const channelMessages = useMemo(() => {
  if (chatMode) return messages.filter((m: any) => m.channel === "chat");
  // Email 模式：显示 email 消息 + 无 channel 的旧消息（兼容历史数据）
  return messages.filter((m: any) => !m.channel || m.channel === "email");
}, [messages, chatMode]);
```

### 两种模式如何互不干扰

1. **数据层面**：Message.channel 在写入时区分 — POST `/messages` 带 `channel: "email"`，ChatWindow 和 chat-messages API 带 `channel: "chat"`
2. **展示层面**：同一对话的消息列表里可能同时有 email 和 chat 消息，但前端通过 `channelMessages` 过滤只展示当前 tab 的消息
3. **发送层面**：Email 模式用 `Textarea` + `sendReply()`，Chat 模式用 `ChatWindow` 组件。两个发送逻辑互不干扰
4. **但有一个隐患**：如果用户在 email 模式发了消息然后切到 chat 模式，email 消息会消失——不是 bug，是设计。但用户可以同时开两个 tab（同一对话的 chat 和 email），这在多人协同时可能引起混淆

```
左侧 w-72（隐藏 md:以下）         中间 flex-1                    右侧 w-80（仅 xl:以上）
┌──────────────────┐  ┌──────────────────────────┐  ┌─────────────────────────┐

│                  │  │ AI 草稿气泡              │  │ ─ 情感与信号            │
│ 点击 → router.push│  │ compose 区（Email 模式） │  │ ─ AI 建议行动           │
│                  │  │ ChatWindow（Chat 模式）  │  │ ─ 重新评分按钮          │
│                  │  │ 翻译预览                  │  │                        │
└──────────────────┘  └──────────────────────────┘  └─────────────────────────┘
```

### 移动端降级

- 左侧列表：`hidden md:flex` — 移动端不显示，改用 router.push 导航
- 右侧面板：`hidden xl:flex` — 平板也不显示，只有大屏幕有
- 移动端 header 有返回按钮：`<Button onClick={() => router.push("/inbox")}>`
- 关键：`/inbox/[id]` 作为直链打开时，移动端全屏展示消息详情，左侧列表隐藏在导航栈后面

### 和普通 inbox 的区别

| 特性 | `/inbox` (InboxClient) | `/inbox/[id]` (InboxDetailClient) |
|------|----------------------|----------------------------------|
| 布局 | 两栏（列表+详情） | 三栏（列表+详情+AI面板） |
| 导航方式 | `setSelectedId()` (state) | `router.push(/inbox/${id})` (URL) |
| AI 分析面板 | ❌ | ✅ |
| 翻译 | ❌ | ✅ |
| 重新评分按钮 | ❌ | ✅ |

## 5. 分页加载的实现细节

### API 层：cursor-based 分页

```typescript
// messages/route.ts — GET handler
const cursor = url.searchParams.get("cursor");  // message ID
const limit = Math.min(parseInt(url.searchParams.get("limit") || "50", 10), 100);

// Cursor 逻辑：找 cursor 消息的 createdAt，取更老的
if (cursor) {
  where.createdAt = { lt: cursorMsg.createdAt };
}

// 取 limit+1 条来判断 hasMore（避免边界误判）
const messages = await prisma.message.findMany({
  where, orderBy: { createdAt: "desc" }, take: limit + 1,
});
const hasMore = messages.length > limit;
if (hasMore) messages.pop();
messages.reverse();  // desc → asc for display
```

### 前端：scrollHeight 位置保持

```typescript
// inbox-client.tsx — loadMoreMessages()
const container = messagesContainerRef.current;
const oldScrollHeight = container?.scrollHeight ?? 0;  // 加载前高度

// ... fetch & setMessages ...

requestAnimationFrame(() => {
  if (container) {
    const newScrollHeight = container.scrollHeight;    // 加载后高度
    container.scrollTop += (newScrollHeight - oldScrollHeight);  // 补偿差值
  }
});
```

**关键细节**：`requestAnimationFrame` 确保在 React 渲染完（DOM 更新后）才计算新高度。`scrollTop += delta` 而不是 `scrollTop = delta`，因为用户可能已经在滚动。

### 三个 cursor state

```typescript
const [nextCursor, setNextCursor] = useState<string | null>(null);  // 下一次加载用的 cursor
const [hasMore, setHasMore] = useState(false);
const [loadingMore, setLoadingMore] = useState(false);
```

- `nextCursor === null` → 没有更多消息
- `hasMore === true && nextCursor` → 显示"加载更早的消息"按钮
- `!hasMore && messages.length >= 50` → 显示"已显示全部消息"
- `messages.length < 50` → 不显示任何提示（首屏数据不够一页，不可能是"已全部"）

## 6. 前端架构的最大风险

### 风险 1：messages state 全量在内存

```typescript
const [messages, setMessages] = useState<Message[]>([]);
```

如果对话有 500 条消息，全量存在 `messages` 数组里。每条消息平均 500 字符的内容 + 元数据，500 条 ≈ 500KB 内存。再加 `filter + map` 的 channelMessages 过滤，每个 re-render 都要跑一遍。

**10x 场景**：5000 条消息 = 5MB state + 每次 channelMessages 过滤扫全数组。需要在 React.memo、虚拟滚动、或分批渲染中选一个。

### 风险 2：channelMessages 的 useMemo 依赖过宽

```typescript
const channelMessages = useMemo(() => {
  // filter logic
}, [messages, chatMode]);
```

`messages` 数组一变化（发送新消息、加载更早消息、收到 WebSocket 消息），整个过滤逻辑重新跑。如果 messages 很长，这个 useMemo 的效果被稀释了。

### 风险 3：两个 inbox 客户端的存在

`inbox-client.tsx` 和 `inbox-detail-client.tsx` 共享约 60% 的逻辑（发送、AI 草稿、分页），但没有抽取共享 hook。修改 sendReply 逻辑要改两处——这是之前漏过的 bug 的根源。

### 10x 改造路径

1. 虚拟滚动（`@tanstack/virtual`）— 消息列表只渲染可见的 20 条
2. 抽取 `useInboxMessages()` hook — 统一两个客户端的分页/发送/草稿逻辑
3. messages 改用 `useReducer` — 统一 append/prepend/update/remove 操作，减少闭包陷阱
4. channelMessages 用 `useDeferredValue` — 在过滤大数组时不阻塞 UI
