# 模块 1：整体架构

## 结论

SalesAgent AI 是一个 **pnpm + Turborepo monorepo**，3 个应用（web/worker/mobile）+ 7 个共享包，通过 workspace 协议互联。部署在 **Vercel (Serverless)** + **Railway (长期容器)** 双平台上，数据层是 **Supabase PostgreSQL + pgvector + Upstash Redis**。架构的核心理念是 **Serverless First、优雅降级、Human-in-the-Loop**。

---

## 1. 为什么是 monorepo？

### 现状

```
apps/
  web/       → Next.js 14, 依赖 shared-types, domain, ai-core, rag-core, api-client, db, ui-tokens
  worker/    → BullMQ Worker, 依赖 ai-core, domain, db
  mobile/    → Expo 52, 依赖 shared-types, domain, api-client, ui-tokens

packages/
  shared-types → 零内部依赖
  domain       → 零内部依赖
  ui-tokens    → 零内部依赖
  api-client   → 依赖 shared-types
  ai-core      → 依赖 domain, shared-types
  rag-core     → 无包依赖（运行时注入 LLM），peer dep on @salesagent/db
  db           → 零内部依赖（纯 Prisma schema + 客户端单例）
```

### 依赖关系图

```
                    ┌──────────────┐
                    │  shared-types│  ← 基础类型（被所有人引）
                    └──────┬───────┘
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │  domain  │    │api-client │    │ ui-tokens│
    └────┬─────┘    └──────────┘    └──────────┘
         │
    ┌────┴─────┐
    ▼          ▼
┌───────┐  ┌──────────┐
│ai-core│  │ rag-core │  ← 运行时 LLM 注入（无硬依赖）
└───┬───┘  └──────────┘
    │
    ▼
┌──────────┐
│ apps/web │──► 消费所有人
└──────────┘
```

### 为什么不用 Nx/Turborepo 的高级功能

当前 Turborepo 只开了 `dev` 和 `build` 两个 pipeline task，没用 remote caching。原因是：
1. 团队规模小（1 人），不需要分布式缓存
2. pnpm workspace protocol (`workspace:*`) 已经解决了本地包依赖
3. 每个 package 独立 typecheck，不会循环引用

### 循环依赖风险

所有包都是 **单向依赖**，`shared-types` 和 `domain` 是纯类型/常量包，不引任何人。`ai-core` 引 `domain`，`rag-core` 不引 `ai-core`。最大的耦合点：`apps/web` 同时引 `rag-core` 和 `ai-core`，但两者之间没有互相引用——这是有意的隔离。

唯一需要注意的地方是 `@salesagent/worker/queue` 被 `apps/web` 的 `messages/route.ts` 和 `score-lead/route.ts` 动态 import：
```typescript
const { scoringQueue } = await import("@salesagent/worker/queue");
```
这是 `web → worker` 的单向引用（web 入队，worker 消费），不会循环。

## 2. Next.js 14 App Router 特性使用

### Server Component vs Client Component 边界

**判断依据**：需要交互=Client，纯数据获取=Server。

```
Server Components（数据获取层）:
  app/(dashboard)/inbox/page.tsx        → prisma 查 Conversation 列表
  app/(dashboard)/inbox/[id]/page.tsx    → prisma 查 Conversation 详情
  app/(dashboard)/analytics/page.tsx     → prisma 聚合（leads, campaigns, agent）
  app/(dashboard)/home/page.tsx          → prisma 聚合（onboarding check, KPI）

Client Components（交互层）:
  app/(dashboard)/inbox/inbox-client.tsx        → 筛选/选中/消息/发送（7 useState）
  app/(dashboard)/inbox/[id]/inbox-detail-client.tsx → 同上 + AI面板
  app/(dashboard)/analytics/ai-metrics.tsx      → 客户端 fetch metrics API
  app/(dashboard)/analytics/ai-health.tsx       → 客户端 fetch + period selector
```

### 为什么不是全部 SSR

1. Inbox 的消息列表需要客户端交互（筛选、选中、发送、AI 草稿审批），SSR 后需要 hydrate，如果全量 SSR 会导致首次 JS bundle 过大
2. Analytics 的时间范围选择是客户端交互，SSR 只能渲染默认视图
3. Server Component 用 `@salesagent/db` 的 PrismaClient 直连 DB——这在 Serverless 下已通过 `connection_limit=1` + pgBouncer 解决

### 用到的关键特性

- `searchParams` — analytics page 的 tab 切换（`?tab=ai|metrics|boss|sales`）
- `params` — 动态路由 `[slug]` / `[id]`
- `loading.tsx` — 每个 dashboard 子路由有独立 loading 骨架
- `error.tsx` — 每个子路由有独立 error boundary（14 个文件）
- Route Handlers — 50+ API routes，全部用 `NextRequest/NextResponse`

### 没用的

- ISR（`revalidate`）— 所有数据都是实时查询，不需要静态再生成
- `generateStaticParams` — 没有静态生成的页面
- Server Actions — 所有 mutation 走 API route，不用 Server Action（保持 Session 在 Route Handler 层统一校验）

## 3. Vercel + Railway 双部署

### 为什么不能全放 Vercel

| 限制 | 影响 | 解决方案 |
|------|------|---------|
| **函数执行时间**：Hobby 10s / Pro 60s | BullMQ Worker 需要长期运行，不是 request-response 模式 | Railway 长期容器 |
| **WebSocket 不支持** | 实时聊天需要持久 TCP 连接 | 独立 socket-server.ts (port 3001)，本地/Railway 跑 |
| **文件系统不持久** | 日志、临时文件在函数销毁后丢失 | 不需要（所有数据存 PostgreSQL/Redis） |
| **并发限制** | Free tier 有限的并发连接数 | Web 够用（大多数是 SSR 数据获取，不是长连接） |

### 双部署的数据流

```
用户 → Vercel (Next.js)
         ├── SSR: 读 PostgreSQL（通过 Supabase 连接池）
         ├── API: 写 PostgreSQL + 写 Redis 队列
         └── 不跑: BullMQ Worker（在 Railway 上）

Vercel 入队 → Upstash Redis → Railway Worker 消费
         └── 出队: conversationQueue.add("compose-reply")
         └── Worker 消费: composeAiResponse() → DeepSeek API → 写 DB
```

### Railway 的配置

`railway.toml` 使用 nixpacks builder（自动检测 Node.js + pnpm），Worker 通过 `npx tsx apps/worker/src/index.ts` 启动。healthcheck 在 port 8080，返回 JSON `{ status, activeJobs, uptime }`。

## 4. 数据模型关系图

### 实体关系图（16 个模型，3 层）

```
┌──────────────────────────────────────────────────────────────┐
│ Layer 1: 租户 & 用户                                         │
│                                                              │
│  User ──< Membership >── Organization                       │
│           (role: owner|admin|operator|viewer)                │
│                                                              │
│  Lead.userId ──> User (Customer Portal 关联, optional)       │
│  ApiKey ──> Organization (onDelete: Cascade)                │
│  FeatureFlag ──> Organization (onDelete: Cascade, nullable)  │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ Layer 2: 业务实体 (全部有 organizationId)                    │
│                                                              │
│  Agent ──< Conversation >── Lead                           │
│   │           │                │                             │
│   │           ├──< Message (onDelete: Cascade)              │
│   │           │      └── aiMetadata (JSON)                  │
│   │           │      └── reviewAction ("approved"|"rejected")│
│   │           │                                              │
│   │           └──< AICallMetric (no FK, soft link by id)    │
│   │                                                          │
│   ├──< Campaign >── CampaignRun                             │
│   │      └── Script (onDelete: no cascade)                  │
│   │                                                          │
│   └── 无直接关系                                             │
│                                                              │
│  Lead ──< LeadActivity (onDelete: Cascade)                  │
│  Lead ──< Conversation                                       │
└──────────────────────────────────────────────────────────────┘

┌──────────────────────────────────────────────────────────────┐
│ Layer 3: 知识库                                              │
│                                                              │
│  Document ──< DocumentChunk (onDelete: Cascade)             │
│              └── embedding (pgvector, Unsupported)           │
│              └── searchVector (tsvector, Unsupported)        │
└──────────────────────────────────────────────────────────────┘
```

### 关键索引

```sql
-- 高频查询优化
Conversation: @@index([organizationId, status, updatedAt DESC])
Message:      @@index([conversationId, createdAt ASC])
AICallMetric: @@index([organizationId, createdAt DESC])
             @@index([organizationId, jobType])
LeadActivity: @@index([leadId, createdAt DESC])
Document:     @@index([organizationId, createdAt DESC])
DocumentChunk: @@index([documentId, chunkIndex])
FeatureFlag:  @@unique([organizationId, key])
```

### 查询瓶颈分析

1. **Message 无分页历史债**（已修复）：之前 `GET /messages` 全量 `findMany`，大对话会扫全表。现在加了 cursor-based `take: limit+1`。
2. **Conversation 列表固定 50 条**：`page.tsx` 的 Server Component 硬编码 `take: 50`，超过 50 个对话的组织看不到后续
3. **AICallMetric 无 kbChunksUsed 列**：KB 命中率无法从 DB 直接聚合，只能从 API response 层统计
4. **DocumentChunk 的向量列在 Prisma 外管理**：`embedding` 和 `searchVector` 标记为 `Unsupported`，通过 `setup-vector.mjs` 和 `$queryRawUnsafe` 手动管理。Prisma migrate 不会删除它们（加了注解），但也不会创建它们

### 软删除 vs 硬删除

- **硬删除**：Conversation → Message（`onDelete: Cascade`），Lead → LeadActivity（Cascade），Document → DocumentChunk（Cascade）
- **无软删除**：没有任何模型有 `deletedAt` 字段
- **"已关闭"替代删除**：Conversation.status = "closed" / "archived"，Lead.stage = "closed_lost"
